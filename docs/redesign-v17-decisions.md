## 결론 (2026-07-31 확정)

**기획은 하나도 안 버린다. 버리는 것은 수치와 구현뿐이다.**

| 층 | 처리 |
|---|---|
| 기획 (L1~L4, 22항목) | **100% 계승** → 통합 기획서 v11이 곧 재설계 명세 |
| 구조 (코드) | **백지** — 신 객체 해체, 전역 가변 상태 제거, 의도 기반 API |
| 수치 (L5) | **백지** — 전면 재튜닝 |

### 이 결론의 중요한 함의
1. **재설계의 목표가 명확해졌다** — "무엇을 만들 것인가"는 이미 다 정해져 있다. 새로 발명할 기획이 없다.
2. **밸런싱이 작업의 절반이 된다** — 수치를 백지에서 다시 잡는다는 것은 코드 작업이 아니라 **기획+튜닝 작업**이다.
   10 스테이지 × 기믹 × (체공·게이지·산개·판정 범위) 를 새로 잡아야 한다.
3. **플레이 검증의 성격이 바뀐다** — "옛 감각이 유지됐나" 확인이 아니라, **"새 감각을 만드는"** 과정이 된다.
   따라서 플레이테스트는 줄어드는 게 아니라 **재설계 후반부에 집중적으로 필요**하다.
4. **불변식 테스트의 대상이 확정됐다** — 위 22항목이 그대로 불변식 목록이 된다.
   예: 4-3 → "목표 초과 시 실패한다"(수치 무관) / 4-2 → "보이는 보드 밖 = 낙"(좌표 무관)

# L6. 재설계 설계 결정 (감각·구조) — 2026-07-31

## 6-1. 공간 구조 ★기반 — **확정**

**판정 공간과 표현 공간을 분리한다.**

| | 정의 | 용도 |
|---|---|---|
| **Board Space** | **완전한 직사각형** (가로로 넓게, 약 16:9) + **높이 h** | **모든 게임 로직**. 돌·손 위치, 줍기/낙 판정, 기믹 이동 |
| **Screen Space** | Board Space를 **사다리꼴로 투영** + h만큼 위로 | **렌더링 전용**. 로직 계산 금지 |

**불변 규칙 — 변환은 양 끝에서 한 번씩만**
```
마우스 입력 ──역변환──▶ [ 로직 전부 Board Space ] ──정변환──▶ 렌더
```

### 이 구조가 없애는 것
- **`SkyFloorY` 개념 소멸** — "이 y 위는 하늘이니 판정 면제"라는 예외가 사라진다.
  던진 돌은 `h > 0`이라 판정 대상이 아니고, **`h = 0`이 되는 순간에만** 사각형 안/밖을 본다.
  → v16에서 고친 "안착 vs 비행" 구분이 **규칙이 아니라 물리로** 자동 해결.
- **판정 폴리곤이 하나뿐** → "어느 함수/어느 폴리곤을 쓸까"라는 질문 자체가 소멸 (버그 6건 중 5건의 원인).
- **손 이동이 균일해짐** — 지금은 뒤쪽에서 커서를 조금만 움직여도 보드상 훅 지나감(사다리꼴 때문).
  Board Space에서 균일하게 움직이고 화면에선 뒤쪽일수록 느리게 보여 원근감이 오히려 맞아진다.

## 6-4. 조작감 설계 결정

### 설계 원칙 — **확정**
> **규칙은 가혹하게, 정보는 완전하게.**
> 즉사 규칙(4-3 초과 줍기 등)은 그대로 둔다. 대신 **몰라서 죽는 일**이 없게 한다.
> 죽는 건 플레이어 실수여야 하고, 정보 부족이어서는 안 된다.
>
> **단, 정보는 "결과 주석"이 아니라 "공간"으로 준다.**
> 예: "이 돌이 잡힙니다"라고 표시하지 않고, **손이 닿는 범위를 선명하게** 보여줘서 스스로 판단하게 한다.

| # | 항목 | 결정 |
|---|---|---|
| 6-5 | 줍기 조작 | **✅ 꾹 누르기 유지** (기획서의 '클릭 없는 자동'은 폐기 — 4-3 즉사와 양립 불가) |
| 6-6 | 줍기 판정 | **✅ 돌 중심점 기준** (기획서의 '면적 100%'는 폐기 — 미구현이었고 너무 빡빡함) |

> → **통합 기획서 v11은 "실제 동작"을 기준으로 쓴다.** 문서를 정답으로 두지 않는다.

### 정보 제공 방식 — 대화에서 도출된 제약 (중요)

"정보를 다 보여준다"를 택했으나, 구체 선택은 **일관되게 오버레이를 거부**했다
(줍기: 돌 하이라이트 ✗ / 받기: 안전영역 표시 ✗ / 뿌리기: 결정론화 ✗).

> **정보는 오브젝트 자체가 말한다. HUD·주석·하이라이트를 얹지 않는다.**
> 손 판정 범위 → **손 그림**으로 · 받기 안전 영역 → **손 모양**으로 · 산개 범위 → **링**으로.
> 게임이 화면 위 설명이 아니라 **물리적 표현으로 읽히게** 한다.

## 6-5. 던지기·받기 체험 설계 — **승인 (2026-07-31)**

### 진단 — 불공평의 원인 2개
1. **화면 y 하나가 "보드 위 위치"와 "높이"를 동시에 표현한다.** `y=-1.0`이 뒤쪽에 놓인 돌인지
   앞쪽에서 떠 있는 돌인지 구분 불가 → `SkyFloorY`라는 임의의 선으로 우회 → 모든 혼란의 근원.
2. **받기가 물리 충돌 판정이다.** 2.5D는 z=0 평면 물리라 결국 **화면 겹침**. 1px 어긋나면
   "분명히 손 위인데" 못 받는다. 게다가 **언제 닿는지 알려주는 정보가 없다.**
→ 공간도 시간도 모호. 둘 다 Board Space + h가 푼다.

### 확정된 체험
| Phase | 설계 |
|---|---|
| 던지기 | 돌은 **제자리에서 수직**으로 솟는다. 보드 좌표 고정, `h`만 오르내림. **그림자가 조준선**이 되어 "여기로 돌아온다"를 약속한다 |
| 줍기 | **그림자의 크기·진하기가 `h`를 표현한다.** 높을수록 작고 흐리게, 내려올수록 크고 진하게. 별도 타이머·게이지 없이 오브젝트가 남은 시간을 말한다 |
| 받기 | `h`가 손 높이에 닿는 순간 **보드 좌표에서** 손 범위 안이면 성공. 중심=손바닥(안착) / 가장자리=손가락(튕김) |

**핵심 갈등 복원:** "하나 더 주울까, 지금 돌아갈까." 지금은 이 정보가 없어 갈등이 아니라 **도박**이다.

|---|---|---|
| 6-12 | 던진 돌 궤적 | **✅ 수직 고정** (그림자 안 움직임) |
| 6-13 | `h` 시각화 | **✅ 그림자 크기·진하기** (별도 UI 없음 — 원칙 준수) |

## 6-6. 손 모델

**현황:** 3D 모델이 아니다. `HandModelBuilder`가 런타임에 **Cube 1개 + Cylinder 5개**로 조립한다.
부자연스러운 것이 당연하다.
