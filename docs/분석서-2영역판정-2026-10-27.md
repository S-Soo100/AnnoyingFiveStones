# 분석서 — B안: 2영역(득점/유예/낙) 판정 도입

> 트랙: Standard — BoardBounds·BoardSpace·GameManager(+선택 시 Stone 시각 1건), 기존 낙 판정 변경.
> 이 분석서 합의 후 구현. 승인 전 코드 수정 없음.

## 0. 목표 한 줄

낙 경계를 "선 하나"에서 "보드 → **유예 밴드** → 낙" 3구간으로 바꿔, 억울한 낙("테이블 위인데 낙")을 없애면서 모서리에 걸친 돌이 만드는 긴장을 게임의 재미로 전환한다. **열받음의 출처를 판정 불신에서 기믹·회귀로 옮기는 것**이 목적이며, 난이도 하향이 목적이 아니다.

## 1. 구간 정의

```
돌 위치 d = 보드 경계(통일 quad)로부터의 바깥 거리 (월드, 경계 안이면 0)
  d == 0            → 보드    (정상 — 현행과 동일)
  0 < d ≤ Band(0.8) → 유예 밴드 (낙 아님. 돌 생존, 줍기 가능, "가장자리" 상태)
  d > Band          → 낙      (현행 실패 흐름 그대로)
```

- 상수: `BoardSpace.FailMargin`(현 0.5)을 `GraceBandWidth = 0.8f`로 개명·승격 — v24에서 예고한 대로 이 상수가 밴드 폭이 된다. **폭 0 = v22 동작, 0.5 = v24 동작**과 수학적으로 동일(낙 경계 기준)이라 되돌리기는 상수 하나다.
- 신규 질의: `BoardBounds.IsInGraceBand(pos)` — 낙은 아니지만 보드 밖. 시각 연출·통계·후속 기믹의 훅.

## 2. 가정 (전부 코드 실측 — 2026-10-27)

- ✅ **밴드 돌 줍기는 추가 코드 없이 이미 성립한다.**
  - 손 커서 추종(`UpdatePosition`)에 x·y 클램프 없음 — 손이 보드 밖까지 자유 이동 (`boardMin/Max`는 받기 y 하한 전용).
  - 줍기 판정(`IsStoneUnderHand`)은 무클램프 보드좌표 거리 — 밴드 위치에서도 정상 계산.
  - `TryHoldPickStones`는 `State.OnBoard`만 요구 — 밴드 돌도 OnBoard면 집힌다.
- ✅ 손 그림자는 보드 밖 1.2u에 걸쳐 페이드(`UpdateHandShadow`) — 밴드(0.8u)에서 옅어지되 보인다. 추가 작업 불필요.
- ✅ 낙 판정 소비자는 GameManager 2곳뿐(`CheckMatBoundaryGlobal` 305행 / `CheckOnBoardStonesOutOfBounds` 393행, v24에서 전수 grep).
- ✅ **뿌리기 낙은 별도 경로** — `ScatterSystem`이 `ContainsWithMargin(board, BoardMarginUnits)`로 보드좌표에서 자체 판정(하늘 면제 없는 Strict 계열). 밴드와 독립이며, 밴드 적용 여부는 §4-1의 결정 사항.
- ✅ 돌이 밴드로 가는 경로: OnBoard 돌은 비-kinematic이라 물리 접촉(돌끼리·방해물)으로 밀릴 수 있다(v19 주석). 도망 공기·뿌리기 배치는 Strict 클램프로 보드 안 유지 — **밴드는 "사고의 착지 지점"으로만 존재**.
- ⚠️ 미확인: 방해물(5단) 공이 돌을 0.8 이상 밀어내는 빈도 — 구현 후 플레이 실측으로 확인(§7).

## 3. 변경 범위 (파일/함수 수준)

| 파일 | 변경 |
|------|------|
| `BoardSpace.cs` | `FailMargin` → `GraceBandWidth = 0.8f` 개명(주석에 v24 호환 명시) |
| `BoardBounds.cs` | `IsInGraceBand(Vector2)` 추가 = `!IsOutsideMatStrict(pos, 0f) ? false : !IsOutsideMat(pos, GraceBandWidth)` 류의 조합. 기존 `IsOutsideMat` 시그니처 불변 |
| `GameManager.cs` | 낙 2곳: 마진만 `GraceBandWidth`로 (사실상 v24 코드에서 상수명 교체) |
| `Stone.cs` (옵션 C-2 채택 시) | 밴드 진입 시 미세 흔들림 or 틴트 — §4-2 결정 후 |

핵심: **판정 수학은 v24에서 이미 완성**(마진 확장). B안의 실체는 ①폭 0.5→0.8 ②`IsInGraceBand` 훅 신설 ③(선택) 시각 연출 ④설계 의미 부여다. 구현 리스크가 낮은 이유.

## 4. 선택지와 추천

### 4-1. 뿌리기 낙에도 밴드를 적용할까?
- **(a) 미적용 (추천)** — 뿌리기는 "조준 실력"의 영역이라 엄격 유지. 밴드는 플레이 중 밀림·튕김 사고만 구제. 낙 확률 밸런스(미결)를 흐리지 않는다. "뿌리기는 내 탓, 밀림은 봐준다" — 열받음의 공정성 문법과 일치.
- (b) 적용 — 뿌리기 낙 확률이 즉시 내려간다. 밸런스 숙제와 얽혀 효과 분리가 안 됨. 비추천.

### 4-2. 밴드 돌 시각 처리
- **(a) 무표시 (추천, 1차)** — 아트 테이블 모서리가 이미 시각 단서. §8 "오브젝트가 말한다"의 최소 해석. 구현 0.
- (b) 미세 연출 — 밴드 돌만 살짝 흔들림(0.5~1px 진폭) 또는 그림자 진하게. "아슬아슬" 긴장 강화. 1차 테스트에서 밴드 인지가 안 되면 추가.

### 4-3. 밴드 폭
- **0.8 고정 출발 (추천)** — 35단 격차(최대 ~1.0)의 대부분 흡수 + 테이블 밖 과도 생존 방지. 라이브 튜닝 대상으로 Inspector 노출은 하지 않고(소비자가 상수 직참조) 상수 수정으로 조정.
- 스테이지별 폭은 **도입하지 않는다** — v17 "보드 정의는 하나" 원칙. 필요해지면 그때 별도 합의.

## 5. 유저 체험 시뮬레이션 (GATE 3.5)

**장면 1 — 방해물 단(30살), 공이 돌을 쳐냈다:**
- [화면] 돌 하나가 패드 모서리 밖으로 밀려나 테이블 가장자리에 멈춘다. FAIL이 뜨지 않는다.
- [조작] 플레이어가 "죽은 줄 알았는데?" 하며 손을 가장자리로 가져가 줍는다.
- [반응] 평소와 같은 줍기 — 집힌다.
- [감정] "휴, 살았다" + "이 게임, 억울하게 죽이진 않는구나" (판정 신뢰 ↑). 열받음은 방해물 공 자체에 남는다.

**장면 2 — 돌이 더 세게 밀려 테이블을 완전히 벗어난다:**
- [화면] 돌이 밴드도 지나 떨어진다 → FAIL "낙!" (현행 동일).
- [감정] "저건 어쩔 수 없지" — 시각적으로 명백히 밖이라 수긍.

**변하지 않는 것:** 뿌리기 낙, 받기/UNDERPICK/초과줍기, 회귀 루프, 모든 기믹 — 전부 현행 그대로.

## 6. 실패 시나리오

1. **밴드 돌을 손이 못 집는 레어 케이스** — 코드상 성립 확인됐으나, 돌이 화면 하단 여백(y < 앞변-0.8 부근)에 걸치면 커서 도달은 되지만 원근 스케일 클램프 경계라 체감이 어색할 수 있다 → 플레이 실측 항목.
2. **밴드 생존 돌이 도망/색선택 기믹 로직과 충돌** — Flee 이동은 Strict 클램프라 밴드 돌을 쫓아 나가진 않음(코드 확인). ColorSelect 추가 돌 스폰 위치는 보드 안 — 영향 없음. 잔여 리스크는 기믹별 스모크로 확인.
3. **과도한 관대함 체감** — 폭 0.8이 커 보이면 0.6으로 즉시 하향(상수 1개).

## 7. 검증 방법 (구현 후, 사용자 테스트 요청 전 자체 수행)

1. 재컴파일 0에러 + EditMode 15/15.
2. `script eval`로 돌을 밴드 좌표에 강제 배치(`transform.position` 세팅) → 1프레임 뒤 낙 미발동 + `IsInGraceBand=true` 확인, 밴드 밖 배치 → 낙 발동. 경계 3점(quad+0.7 / +0.8 / +0.9) 샘플.
3. 직접 플레이: 5단(방해물)에서 공 충돌로 밀린 돌 관찰, 밴드 생존 → 줍기까지.
4. 사용자 확인: 모서리 아슬 돌의 손맛(줍기 체감), 폭 0.8의 관대함 체감.
