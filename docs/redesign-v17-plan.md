## 3. 근본 원인 3가지

### R1. 전역 가변 상태 — "누가 언제 바꿨는지" 추적 불가
`BoardBounds`가 전부 `static`이고, `SetQuadOverride`가 `SkyFloorY`까지 **부수효과로** 갱신한다.
스테이지 전환 타이밍에 따라 값이 달라지는데(`HasQuad`는 씬 init 시 false → 스테이지 시작 후 true),
읽는 쪽 13파일 69곳은 그 타이밍을 알 수 없다.

### R2. 신 객체 — 책임이 섞여 변경이 전이됨
- **HandController 1,610줄** = 커서추종 + 입력 + 줍기 + 던지기 + **5단 전용 시퀀스(약 570줄)** + 손 포즈/손가락 애니메이션 + 고스트 + 디버그 오버라이드
- **GameManager 1,019줄** = 페이즈 머신 + 스테이지 진행 + **전환 연출 코루틴(약 250줄)** + 낙 감시 + 입력(ESC) + 디버그 점프 + 가이드 텍스트
- **5단이 전 계층에 특수 분기로 누출**: `GamePhase`에 `Stage5Throw`/`Stage5Catch`, `GameManager.stage5Step`, `HandController`의 570줄. 5단을 건드리면 1~4단이 깨진다.

### R3. 검증 수단 부재 — 회귀를 사람 눈으로만 잡음
테스트가 0개라 "고쳤다"의 근거가 매번 수동 플레이다. 감사 로그의 반복 실패(v9/v11×3/v12×2/v14×5/v16)가
전부 **"고쳤다고 보고 → 유저가 반례 발견"** 패턴인 이유.

> **R1·R2가 버그를 만들고, R3이 그 버그를 늦게 발견하게 한다.** 셋을 같이 풀지 않으면 재설계해도 재발한다.

## 4. 방법론 — 왜 빅뱅 재작성이 아닌가

**이 게임의 가치는 코드가 아니라 손으로 튜닝한 수치에 있다.** 게이지 곡선, 토스 duration, hop 0.09,
낙하 2.2s, 간격 `sep`, 5단 캐치 윈도우 등 수십 개가 플레이 감각을 결정한다.
전면 재작성하면 수치를 옮겨도 **호출 순서·프레임 타이밍이 바뀌며 감각이 달라지고, 달라졌는지 알 방법이 없다**(R3).

→ **Strangler Fig 방식**: 새 구조를 옆에 세우고 호출부를 하나씩 옮긴다.
→ **Phase 0에서 안전망을 먼저 만든다.** 이게 이 계획의 핵심이고, 여기를 건너뛰면 나머지가 전부 도박이 된다.

### 작업 격리 (착수 전 필수)
현재 같은 워킹트리에 **다른 Claude 세션이 떠 있다.** Critical 작업은 반드시 별도 worktree + 브랜치(`redesign/v17`)에서.
Phase마다 main으로 머지하고, 각 머지 지점은 **게임이 플레이 가능한 상태**여야 한다.

## 5. Phase 계획

각 Phase의 종료 조건은 공통으로 **(a) 게임 플레이 가능 (b) 테스트 전부 green (c) 수동 체크리스트 통과**.

### Phase 0 — 안전망 구축 ★가장 중요, 건너뛰기 금지
**목표:** 현재 동작을 "정답"으로 박제한다.

1. `.asmdef` 도입 (`FiveStones.Runtime` / `FiveStones.Tests`) — 지금은 없어서 테스트를 붙일 수 없다
2. **EditMode 골든 테스트** — 순수 계산만 대상. MonoBehaviour 불필요:
   - `BoardBounds`: `QuadPoint` bilinear 매핑, `IsOutsideMat` / `IsOutsideMatStrict` 경계값, `SkyFloorY` 자동 동기화
   - 10개 스테이지 `BoardQuad` 전부에 대해 격자 샘플링 → 내부/외부 판정 스냅샷
   - `ScatterSystem`의 게이지→uv 반경 곡선, 타겟 계산(`TrapPoint`)
   - **오늘 고친 낙 판정은 "새 정답"으로 기록** (구 동작을 박제하면 안 됨)
3. **수동 플레이 체크리스트** 문서화 — 10단 × 핵심 동작. 자동화 못 하는 I4·I5용

**산출물:** 테스트 프로젝트 + 골든 스냅샷 + 체크리스트
**리스크:** 낮음 (프로덕션 코드 변경 0)

### Phase 1 — 도메인 로직 추출 (R1 해소)
**목표:** 좌표·판정·곡선을 MonoBehaviour 밖 순수 클래스로. 여기가 버그 6건 중 5건이 살던 곳.

1. `BoardGeometry` (순수, 불변 객체) — quad 4점을 생성자로 받고 `SkyFloorY`는 **파생 프로퍼티**(부수효과 제거)
2. **의도 기반 API** — 호출자가 공식을 고르지 않고 상태만 말한다:
   ```csharp
   bool IsOutside(Vector2 p, StoneMotion motion)  // InFlight(하늘 면제 O) / OnBoard(면제 X)
   ```
   구 `IsOutsideMat`/`IsOutsideMatStrict`는 private화 → **오늘 같은 오용이 컴파일 단계에서 불가능**
3. `ScatterSolver` — 게이지 → 타겟 배열 계산을 순수 함수로 (코루틴/연출과 분리)
4. `BoardBounds`는 얇은 파사드로 남겨 69곳 호출부를 점진 이전

**산출물:** 순수 도메인 3종 + 호출부 이전
**리스크:** 중 — Phase 0 테스트가 방어

### Phase 2 — 신 객체 해체 (R2 해소)
1. **5단 분리 최우선** — `HandController`의 570줄을 `Stage5Sequence`로 독립. `GamePhase`의 `Stage5*` 2개를
   일반 페이즈 + 기믹 상태로 흡수 검토 → 5단 변경이 1~4단에 전이되지 않게
2. `HandController` → 커서/입력 / 줍기·던지기 / 손 비주얼(포즈·손가락·고스트)로 3분할
3. `GameManager` → 페이즈 머신 / 스테이지 진행 / 전환 연출(코루틴) / 낙 감시로 4분할
4. `GameManager.SafeZoneMin/Max` 제거 (유일 소비자 MonochromeGimmick만 남음 — v14에 근거 소멸)

**리스크:** 높음 — 파일당 순차 진행, 각 분리마다 플레이 검증

### Phase 3 — 전역 상태 축소
21 싱글턴 / 276 `.Instance` / 31 `Find*` 정리. **전부 없애는 게 목표가 아니다** — Unity에서 일부 싱글턴은 합리적.
목표는 **가변 전역 상태**를 줄이는 것. 읽기 전용 서비스(AudioManager 등)는 유지 가능.

### Phase 4 — UI 계층 정리
런타임 코드 생성 UI(GameUI 868 / TitleScreenUI 845 / PauseMenuUI 631 / SettingsPopupUI 513)의 중복 제거.
**가장 낮은 우선순위** — 버그 이력이 여기엔 거의 없다. Phase 3까지 하고 멈춰도 목적은 달성된다.
